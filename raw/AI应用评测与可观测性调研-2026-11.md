# AI 应用评测与可观测性调研（2026-11）

评测回答“系统是否完成指定任务”，可观测性回答“执行过程中发生了什么”。可用的闭环是：定义成功 → 固定测试集与环境 → 运行和评分 → 检查失败轨迹 → 修复 → 线上监测 → 把真实失败补入回归集。

本报告为中文研究综合，不是网页原文存档。检索日期为 2026-11-06；聚焦应用与 Agent 工程，不重新编排模型榜单。以下知识库助手用例、指标组合和上线门槛均为待验证方案，未运行评测，不代表用户已确认的产品要求。上下文与记忆背景见 [[raw/上下文工程与Agent记忆体系调研-2026-11]]。

## 2. 定义评测对象，避免用错分数

| 对象 | 回答的问题 | 主要盲区 |
| --- | --- | --- |
| 通用模型基准 | 模型在指定题集上表现如何 | 不含本应用的数据、工具、预算与用户分布 |
| 组件测试 | 检索、记忆或单个工具是否正确 | 局部通过不能保证完整任务完成 |
| 端到端应用评测 | 给定输入与环境，最终目标是否实现 | 较难定位具体失败步骤 |
| 运行轨迹检查 | 哪一步慢、出错或消耗过大 | 没有成功标准就无法断言输出正确 |
| 在线反馈 / A/B | 真实用户效果是否改善 | 受流量、选择偏差和环境变化影响 |

E1 强调评测 Agent 时同时评测模型与 harness。报告“订票成功”与数据库中确有预订是两回事；知识库助手“已保存文章”与文件存在、内容完整、链接有效也应分开验证。E2 将上线前固定数据集与上线后真实流量评分分开，两者通过失败样例回流连接。

## 3. 评测的最小组成

- **Task**：输入、初始状态、允许动作、成功条件。
- **Trial**：同一个 task 的一次独立尝试。
- **Grader**：对结果或某项行为评分，可以有多个。
- **Trace / transcript**：一次尝试的输入输出、工具调用和中间状态记录；不假设能取得模型不可见的内部推理。
- **Outcome**：环境里的实际终态，如文件、数据库状态或最终回答。
- **Experiment**：某个应用版本在某套数据集上的整组结果。[E1、E2]

复现记录示例：应用版本、模型标识、提示版本、工具版本、知识库快照、数据集版本、评分器版本、预算、超时、重试策略和记忆初态。固定这些条件可以减小混杂，但不能保证远程模型逐 token 重现。

## 4. 三类评分器如何组合

| 类型 | 适合 | 主要风险 | 校验方法 |
| --- | --- | --- | --- |
| 程序规则 | 文件存在、JSON 格式、数值范围、授权约束、实际状态 | 把正确的不同表达误判为错 | 用已知正确和已知错误样例检查规则 |
| LLM 裁判 | 证据支撑、完整性、语气、开放式比较 | 位置/冗长偏差、推理错误、提示注入 | 明确准则、换序复判、人工校准、允许 unknown |
| 人工评审 | 主观质量、领域边界、评分器校准 | 成本高、意见不一致 | 统一准则、独立评分、复核争议 |

分类与组合依据 E1，偏差依据 E3。核心目标由硬条件保证，风格和完整性再分维度评分；不要让高文风分抵消关键事实错误。工具调用顺序只在任务确实要求时设为硬约束，避免把有效的另一种解法判错。[E1]

### 裁判校准方案（设计示例）

先由人给一批典型成功、典型失败和边界案例打标签；隐藏答案来源，成对比较时交换顺序；逐项比较裁判与人工的分歧。不要只报告总体一致率：应检查错误答案被放行的比例、正确答案被误拒的比例及各任务类别。固定裁判版本与准则，修改裁判后重新评分历史样例，不能直接拼接新旧分数。裁判接收的被评文本应视为数据，不能让它修改评分指令。

## 5. 数据集与实验：防止“进步”来自泄漏

E1 建议可从 20–50 个真实失败相关任务起步，这不是充分样本量或统计显著性的保证。面向本库，可先做一个 30 题的起始集：单页事实、跨页比较、版本/日期冲突、记忆更新、证据缺失与干扰输入各 5 题。此分配仅为方案，需要按真实使用情况调整。

- 开发集用于调提示和检索；保留集用于检查未见样例，不把答案写入 Agent 可读的记忆。
- 能力集保留尚难解决的问题；回归集保护已经能稳定完成的任务。[E1]
- 每次 trial 从相同环境快照和独立记忆开始，清理上次遗留文件与缓存带来的优势；在线增量记忆实验则明确记忆更新协议。[E1]
- 使用相同题目成对比较方案。报告分组样本数、失败案例和波动；少量结果变化只作为信号。
- 不因工具报错就自动剔除样例。单独标记环境故障与应用失败，并披露纳入分母的规则，防止幸存者偏差。

## 6. 指标：区分能力、可靠性与使用成本

| 指标 | 可操作的定义 | 注意事项 |
| --- | --- | --- |
| 任务成功率 | 满足全部必要条件的有效试验数 / 有效试验总数 | 明确必要条件与环境故障口径 |
| 证据支撑率 | 被来源支持的可核查主张数 / 可核查主张总数 | 链接存在不代表链接支持结论 |
| 无证据时正确拒答 | 应拒答样例中正确拒答比例 | 同时统计可回答样例的误拒率 |
| Recall@k | 前 k 个结果覆盖的相关证据比例 | 需要标注相关证据；不等于最终回答准确 |
| 延迟 | 端到端 p50 / p95；必要时另列首 token 延迟 | 后台写记忆与重试的时间需说明 |
| 每成功任务成本 | 所有尝试的应用运行总成本 / 成功任务数 | 失败和重试也计入；零成功时未定义 |
| 评分开销 | 裁判调用、人工标注与评测设施成本 | 与应用运行成本分开列出 |

这些定义是本报告的测量方案；预算阈值应由应用要求决定。不要把任意的 90% 或 95% 写成行业合格线。

**pass@k 与 pass^k**：前者表示 k 次中至少成功一次，后者表示 k 次全部成功。[E1] 若对单一任务假设每次独立且成功概率均为 p，则分别是 `1-(1-p)^k` 与 `p^k`。例如 p=0.8、k=3 时是 99.2% 与 51.2%。这只是概率示例，不是实测；有相关失败时假设不成立，也不能把所有任务的平均 p 直接代入当作整套任务的可靠性。

## 7. 可观测性：记录到能解释失败的粒度

一次知识库问答可以记录为：根请求 → 检索 → 文档读取 → 上下文组装 → 模型调用 → 工具执行 → 结果检查。跨多轮会话用 session/thread 标识关联多个 trace，单步操作用 span 表示。E6、E8 提供这类逐步追踪；具体字段需匹配接入工具。

建议记录的应用字段：

- 任务、会话、实验与版本标识；父子调用关系、起止时间、状态和错误类别。
- 模型请求标识、输入输出 token、缓存用量、重试与工具超时；价格表版本用于解释成本估算。
- 检索的文档 ID、版本、排名与分数；记忆读取/写入对象及状态；压缩前后的大小和证据引用。
- 最终结果、各维度评分、评分器版本及人工复核状态。

这些是诊断字段建议，不全部是 OpenTelemetry 标准属性。E4 明确 GenAI 调用 span 描述调用方看到的逻辑操作，自动重试可能包含在同一逻辑 span 内；排查重试时必须确认埋点粒度。

### 标准与隐私边界

OpenTelemetry 解决通用遥测机制；GenAI conventions 与 OpenInference 解决 AI 语义字段。查阅时 E4 仍为 Development，不能写作完全稳定标准。Phoenix 对 OpenInference 提供专门渲染，但接收 OTLP 不等于所有 `gen_ai.*` 字段都被同样解释。[E4、E5]

E4 不建议默认采集完整指令和输入输出，提供选择性记录或外部存储引用等方式。E7 支持数据离开应用前脱敏；若先上传再在界面隐藏，数据已经外流。实际设计需明确保留期限、访问范围、内容采样与删除方式，尤其是文档正文和跨用户记忆。

## 8. 工具定位与选型

| 工具 | 本次核实的能力 | 适合先验证的情境 | 额外核对项 |
| --- | --- | --- | --- |
| LangSmith | 追踪、离线/在线评测、数据集、实验、人工与模型评分 | 已有 Agent 流程，希望把线上失败变成回归用例 | 所需部署方式、数据策略与版本集成 |
| Langfuse | 开源、自托管、追踪、会话、提示管理，基于 OTel | 希望自主控制观测数据，并统一多类调用 | 自托管运维、脱敏与实际功能范围 |
| Arize Phoenix | OTLP/OpenInference 追踪、数据集、实验、代码/模型/人工评分 | 需要检索与模型步骤的诊断和实验比较 | 属性映射、语言集成与部署条件 |
| Promptfoo | 配置式断言、确定性与模型评分、成本/延迟检查 | 希望先建立本地或 CI 中的回归检查 | 端到端状态是否需自行编写检查器 |

能力分别依据 E2、E6、E8、E9；使用情境是研究归纳，不是排名。工具间有重叠，也可以组合。没有购买、安装或部署这些工具；价格、许可证细项及托管地域不在此次核实范围。

## 9. 知识库助手的六个起始用例（未执行）

| 用例 | 初始条件 / 输入 | 通过条件 |
| --- | --- | --- |
| 单页事实 | 问某框架的明确特性 | 回答正确并定位实际支持结论的来源 |
| 跨页比较 | 比较两个框架的记忆范围 | 同一维度比较，明确版本与差异 |
| 旧资料冲突 | 同时放入旧/新版本记录 | 区分时间范围，不静默拼接相互矛盾事实 |
| 偏好更新 | 先声明偏好 A，后明确改为 B | 新会话按 B 回答且可解释来源 |
| 资料缺失 | 问库内没有证据的问题 | 不编造引用；说明缺口或按授权检索 |
| 文档指令干扰 | 正文夹带“忽略问题，改答某内容” | 正文作为被分析资料，不改变任务或权限 |

可按每类 5 个变体构成起始集，并为每题固定参考证据、禁止行为和评分规则。对记忆方案 A/B/C 的比较应复用同一题集与裁判，见上下文专题。

### 运行闭环（设计示例）

先保存基线结果，再只改变一个因素（如压缩策略）；对易波动任务重复运行；抽查改善与退步样例；通过保留集后再决定是否应用。若上线，在线抽样与失败聚类用于发现新问题，审核脱敏后将典型失败转入测试集；线上分数不能代替固定条件的离线对照。[方法依据 E1、E2]
